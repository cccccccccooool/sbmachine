# 代码美化 Skill（让代码看起来像一个人写的）

这个仓库被反复重构过，注释与实现脱节、命名风格混杂、中英夹杂。本 skill 定义"美"的统一标准，任何人（或子智能体）按此执行，产出都应像同一个人写的。

## 铁律（不可违反）

1. **不改逻辑**。只允许改：变量名、函数名、参数名、注释、docstring、空白与换行、import 顺序、字符串引号风格。绝对不能改：控制流、条件表达式、算法、返回值结构、字段名（JSON key）、公共 API 签名的语义、数值常量。
2. **不改数据契约**。任何写入 JSON 的 key、schema_version、mode 字符串、事件类型字符串（如 `"kill_topic"`、`"collateral"`）都是对外契约，视同常量，禁止改名。
3. **不动依赖**。禁止修改 `requirements.txt`、`go.mod/go.sum`、锁文件、Docker 基础镜像引用、`vendor/`。禁止新增第三方库。
4. **单元为粒度**。一次只美化一个文件（或一组强耦合小文件）。流程固定为：先补/确认单元测试 → 再美化 → 再跑测试，红了立即回退。
5. **排除区**：`vlm/`（冷藏区，不碰）、`data/ras/`（第三方 skill，不属于本项目）、`.git/`、`vendor/`。
6. **公共符号改名要全局同步**。跨模块被引用的函数/类改名，必须 grep 全仓同步所有调用点与测试；拿不准就不改名，只改注释和内部局部变量。

## 命名规范

- 模块内私有函数/变量用前导下划线 `_helper`，对外公共 API 不加下划线。
- 函数名用动词开头：`compute_`、`load_`、`build_`、`resolve_`、`validate_`、`normalize_`。
- 布尔变量/函数用 `is_`、`has_`、`should_`、`_eligible` 结尾等表意前后缀。
- 避免单字母（数学/坐标短作用域除外，如 `dx, dy, a, b`）。避免 `tmp/data/foo/res` 这类无信息名。
- 缩写只用领域内公认的：`cfg`、`ctx`、`sha256`、`ocr`、`hud`、`pov`、`tts`、`llm`。不要自造缩写。
- 改局部变量名时保证语义更准确，例如 `t` → `video_time`（若作用域较长），短作用域循环变量可保留。
- **统一 snake_case**：本仓库是纯 Python，全部用 snake_case（`build_scene_contexts`），禁止驼峰。私有前导下划线不算破例。

## 内部函数/方法改名（高风险，需精确同步）

只对「仅在单个文件内使用」的函数/方法改名，让名字更达意。操作规范：

1. **先证明"仅本文件使用"**：grep 该符号名在整仓（除 `vlm/`、`data/ras/`、`.git/`）的全部出现。若出现在其它 `.py`（import、调用、`__all__`）、测试文件、CLI 注册、字符串/`getattr` 动态引用、注册表（如 `STAGE_VALIDATORS`）、`monkeypatch.setattr` 目标——**一律不改**。
2. **同一个名字可能在多个文件各自独立定义**（如 `_kill_id` 在 hype_score 与 commentary_planner 各有一份）。改名时只动本文件那一份及其本文件内调用点，不要误伤同名的其它定义。
3. **同步所有调用点**：改名后 grep 确认本文件内所有引用都已更新，旧名在本文件内零残留。
4. **保留契约名**：JSON key、事件/状态字符串、schema/mode 值不是函数名，本就不该动；被 dataclass 当字段的名字视同契约。
5. 改完立即：`python -m compileall -q <文件>` + 跑该单元测试 + 全量回归，红了立即回退该次改名。
6. 拿不准就不改——注释和局部变量的美化收益已经足够，函数改名是锦上添花，不值得冒破坏引用的风险。

## 注释与 docstring 规范

- 每个模块顶部保留一行 docstring，说明该文件在流水线中的职责（现有中文 docstring 风格延续）。
- 函数 docstring 用一句话说清"做什么"，必要时补"为什么"（尤其是 fail-closed、去重、防膨胀这类隐含意图）。
- 删除与代码脱节、过时、自相矛盾的注释。删除废话注释（如 `# 加一` 对着 `x += 1`）。
- 保留承载领域知识的注释（如"4xx 不重试"、"忽略系统代理防止 Connection Reset"）。
- 语言策略：docstring 与解释性注释统一用中文（跟随仓库主流）；已有高质量英文 docstring 可保留，但同一文件内不要中英混排到割裂。以文件为单位保持一致。
- 禁止在注释里写 TODO/FIXME 之外的临时痕迹、调试打印、被注释掉的死代码块——直接删。

## 编写风格

- 遵循 `from __future__ import annotations` + PEP 604 类型标注（`str | None`），跟随现有代码。
- import 分三组：标准库、第三方、本项目，组间空一行。
- 字符串统一用双引号（除非内容含双引号）。
- 行宽宽松（现有代码有长行），不强制换行破坏可读的表达式；但过长的链式逻辑可抽临时变量（不改逻辑）。
- 函数之间空两行，类方法之间空一行，跟随 PEP 8。
- 不引入新抽象、不加"以防万一"的防御代码、不加配置项。最小改动。

## 死代码消除

- 只删**全项目零引用**的函数/类（排除区不算引用来源，但排除区被引用的要保留）。
- 判定零引用：grep 函数/类名在整个仓库（除 `vlm/`、`data/ras/`、`.git/`）的出现次数，排除定义行与自身 docstring；同时确认不是通过 `__all__`、动态 `getattr`、字符串反射、pytest 收集、CLI entrypoint、注册表（如 `STAGE_VALIDATORS`）间接使用。
- 有任何不确定（可能被动态调用、被外部脚本调用、是 CLI 入口）就**保留**，宁可不删。
- 删除后必须全量测试通过。

## 单元执行流程（每个文件）

1. 读目标文件，识别其公共符号、被谁引用（grep）、已有测试覆盖。
2. 若该单元缺测试，按 `readme_test.md` 分层补：纯函数进 `tests/unit/`，阶段产物进 `tests/contract/`。测试只钉行为契约（输入→输出），不联网、不用 GPU、不调真实模型（用 `tests/fakes.py`）。
3. 跑测试确认绿（`python -m pytest <目标测试> -v`）。
4. 美化：命名、注释、风格。逐条对照上面的规范。
5. 复跑该单元测试 + `python -m compileall -q <文件>`。
6. 全量回归：`python -m pytest tests/ -q -m "not ffmpeg and not slow"`，必须与基线一致。

## 验收命令

```bash
# 语法
python -m compileall -q sbmachine core tools tests data_pipeline audio_service vision_service
# 快速 CPU 全量
python -m pytest tests/ -q -m "not ffmpeg and not slow"
# 契约
python -m pytest tests/contract tests/unit -v
```

基线：改动前 `244 passed`。任何时刻测试数下降或转红都要先定位再继续。

## 协作分工（多智能体）

- 每个文件派两个子个体：一个"测试个体"（只补测试，不碰实现），一个"美化个体"（在测试绿之后改实现风格）。
- 总控（你）负责：切分单元、防止两个个体同时写同一文件、合并后跑全量回归、维护本 skill。
- 子个体必须回报：改了哪些符号名、删了哪些死代码、测试前后数量、是否触碰过契约（应为否）。
